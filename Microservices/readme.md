## Введение в микросервисы

`Микросервисы` - это в первую очередб архитектурный стиль, который разделяет приложение на небольшие сервисы. Тут нам с вами надо уточнить одну деталь. То что вы в одном .sln файле создаете несколько проектов не делает ваш проект микросервисным. Ключевой момент в данной архитектуре это то, что каждый сервис работает в отдельной сети и имеет свой собственный набор данных(на счет данных у меня есть собственное мнение).

Если взять за пример какой-то реальный проект то на официальном сайте msdn уже есть готовый проект и его архитектура. Вот картинка:

![](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/multi-container-microservice-net-applications/media/implement-api-gateways-with-ocelot/eshoponcontainers-architecture.png)

Вы можете подумать что данный подход очень хорош, и его обязательно стоит использовать. Но это не так. Для того чтобы понять стоит ли использовать микросервисы вам надо понять преимущества и недостатки данной архитектуры.

## Преимущества и недостатки микросервисов

Начнем с того что создавать проект с нуля на данной архитектуре не совсем правильно. Для этого заранее нужно провести анализ и понять стоит ли использовать микросервисы. Для маленьких и средних проектов он не подходит. Да и для больших проектов он подоходит в 2 случаях:

1. Вы будете часто обновлять ваши сервисы и ваш продукт сильно коммерческий.
2. У вас будет очень много пользователей и вы не знаете в какуб сторону будет развиваться ваш продукт.

Теперь перейдем к преимуществам:

1. `Масштабируемость` - вы можете масштабировать отдельные сервисы, а не все приложение целиком.
2. `Гибкость` - вы можете использовать разные технологии для разных сервисов.
3. `Простота развертывания` - вы можете развернуть отдельный сервис на отдельной машине.
4. `Простота обновления` - вы можете обновить отдельный сервис без остановки всего приложения.
5. `Простота мониторинга` - вы можете мониторить отдельные сервисы.

Теперь перейдем к недостаткам:

1. `Сложность` - сложно создать архитектуру микросервисов.
2. `Цена разработки и поддержки` - для такого проекта вам нужно будет заморочится с серверами и DevOps инженерами.

## Api Gateway

`Api Gateway` - это прокси сервер, который принимает все запросы от клиента и перенаправляет их на нужный сервис. Также он может выполнять роль балансировщика нагрузки.

еще с паттернов вы должны помнить значение слова прокси, так как всегда он будет выполнять промежуточную роль. Давайте лучше разберем логику работы Api Gateway.

В ASP.NET приложениях для его реализации чаще всекго используется библиотека, которая называется `ocelot`. С его помощью мы можем делать очень много полезных вещей. Вот их список:

1. `Routing` - маршрутизация запросов
2. `Load Balancing` - балансировка нагрузки
3. `Authentication` - аутентификация
4. `Authorization` - авторизация
5. `Rate Limiting` - ограничение скорости
6. `Caching` - кеширование

Вот пример конфигурации ocelot:

```json
{
  "ReRoutes": [
    {
      "DownstreamPathTemplate": "/api/{url}",
      "DownstreamScheme": "http",
      "DownstreamHostAndPorts": [
        {
          "Host": "localhost",
          "Port": 5000
        }
      ],
      "UpstreamPathTemplate": "/{url}",
      "UpstreamHttpMethod": ["Get", "Post", "Put"]
    }
  ]
}
```

## Load Balancing

`Load Balancing` - это распределение нагрузки между несколькими серверами. В микросервисной архитектуре это очень важно, так как у вас будет много сервисов и вам нужно будет распределить нагрузку между ними.

Вообще эти спмые балансировщики бывают 2 типов:

1. `Software Load Balancer` - это программное обеспечение, которое распределяет нагрузку между серверами. Примеры: Nginx, HAProxy, Traefik.
2. `Hardware Load Balancer` - это аппаратное обеспечение, которое распределяет нагрузку между серверами. Примеры: F5, Citrix, Barracuda.

Сразу уточню разницу между балансироващиком нагрузки например на NginX и если вы поптыаетесь написать его на Ocelot. Вот пример конфигурации NginX:

```nginx
upstream backend {
    server backend1.example.com weight=5;
    server backend2.example.com;
    server backend3.example.com;
}
```

В случае с первым у вас будут одинаковые сервисы на разных серверах, а в случае со вторым у вас будут разные сервисы на разных серверах. То есть в большом масштабе они не взаимозаменяемы. В банковских, страховых и других крупных проектах используют именно аппаратные балансировщики нагрузки.

## Swarm

Docker swarm - это оркестратор, который позволяет управлять композициями. проще говоря это управление контейнерами.

Представьте что у вас есть несколько `Docker Compsose` файлов и вы хотите их объединить в один. Вот тут вам и пригодится `Docker Swarm`. Вот пример команды:

```bash
docker stack deploy -c docker-compose.yml myapp
```

В docker swarm есть 2 ключевых понятия:

- `Service` - это набор контейнеров, которые выполняют одну и ту же задачу.
- `Stack` - это набор сервисов.

Для того чтобы инициализировать `Docker Swarm` вам нужно выполнить команду:

```bash
docker swarm init
```

Затем вы можете добавить туда свои сервисы. Вот пример:

```bash
docker service create --name myapp --replicas 3 -p 80:80 myapp
```

В данном примере мы создаем сервис с именем `myapp`, который будет иметь 3 реплики и будет слушать порт 80. Последний параметр это имя образа. Вы такжее можете сразу прописать конфигурацию в файле. Вот пример:

```yaml
version: "3.7"

services:
  myapp:
    image: myapp
    ports:
      - "80:80"
    deploy:
      replicas: 3
```

Если у вас допустим есть ASP.NET + React + MS SQL и вы хотите создать две реплики для ASP.NET и одну для MS SQL, то вам нужно будет создать 2 сервиса. Вот пример:

```yaml
version: "3.7"

services:
  myapp:
    image: myapp
    ports:
      - "80:80"
    deploy:
      replicas: 2

  mssql:
    image: mssql
    ports:
      - "1433:1433"
    deploy:
      replicas: 1
  react:
    image: react
    ports:
      - "3000:3000"
    deploy:
      replicas: 1
```

Также тут можно сразу прописать путь к Dockerfile как и с `Docker Compose` с помощью ключевого слова `context`. Вот пример:

```yaml
version: "3.7"

services:
  myapp:
    build:
      context: ./myapp
      dockerfile: Dockerfile
    ports:
      - "80:80"
    deploy:
      replicas: 2

  mssql:
    image: mssql
    ports:
      - "1433:1433"
    deploy:
      replicas: 1
  react:
    build:
      context: ./front
      dockerfile: Dockerfile
    ports:
      - "3000:3000"
    deploy:
      replicas: 1
```

Вот физическая разница между `Docker Compose` и `Docker Swarm`.
В `Docker Compose` у вас есть один файл, а в `Docker Swarm` у вас есть несколько файлов, которые вы объединяете в один.

А контейнеры у вас хранятся по отдельности. Вот пример:

![](https://encrypted-tbn0.gstatic.com/images?q=tbn:ANd9GcT2g1IHOE5lXxn2QlbnpUCvqMGZr_oSbDZHyg&s)

Да, на этой картинке написано что это `Kubernetes`, но в `Docker Swarm` все также.

Стоит сказать что уже все сейчас пользуются `Kubernetes`, так как он более продвинутый и удобный.
Но для начала вам лучше начать с `Docker Swarm`.
